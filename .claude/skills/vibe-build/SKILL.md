# vibe-build — 요청 하나를 완성까지

사용자는 비개발자다. 코드를 보여주지 말고 **화면·동작 기준**으로 소통한다.
모든 단계에서 `.claude/rules/**`와 관련 스킬을 따른다(해당 파일을 만질 때 rules는 자동 로드된다).
아래 단계의 `backend/spec-create` 같은 표기는 **`.claude/skills/{영역}/{이름}/SKILL.md` 파일을 Read 로 읽고 그 절차를 따른다**는 뜻이다. 슬래시 커맨드가 아니며, 같은 이름의 전역 커맨드가 목록에 보여도 쓰지 않는다.

```
0 준비 → 1 요구사항 → 2 범위
→ 3 서버 spec(API 계약 확정) → 4 화면 spec(그 계약으로) → 5 spec 검증(spec-reviewer) + 배치표(묶음 나누기)
→ 6 병렬 개발(서버·화면 묶음별 서브에이전트·워크트리, 최대 4개 동시) → 7 합치기
→ 8 API 문서 → 9 계약 대조
→ 10 리팩토링 → 11 서버 검증 → 12 화면 검증(MCP→e2e) → 13 최종 검증(harness)
→ 14 검증 반영 커밋 → dev merge → 15 보고
```

## vibe-build 모드 (하위 스킬 공통 규칙)

이 흐름에서 하위 스킬을 따를 때는 **"vibe-build 모드"** 다. 규칙의 단일 출처는 **`.claude/skills/COMMON.md` §2** (메인에서는 하위 스킬이 커밋하지 않음 · 워크트리 도우미는 Task별 커밋 · 중간 확인 없음 · spec-run 은 구현 + 테스트까지). 워크트리 커밋들은 7단계에서 작업 브랜치에 merge 되고, 14단계에서 작업 브랜치가 dev 에 merge 된다 (브랜치 흐름 단일 출처: `COMMON.md` §3-B).

## 0. 준비
- 개발 환경이 준비 안 됐으면 vibe-setup 스킬을 먼저 따른다.
- `.harness/runs/`에 같은 작업의 진행 중 run(`DONE` 파일 없음)이 있으면 그 `state.md`부터 읽고 재개한다. 13단계(최종 검증)에서 멈춘 run 이면 `loop.md` 의 미해결 에러부터 본다. `PAUSED` 파일이 있으면 사용자 답을 반영한 뒤 **지우고** 멈춘 단계부터 이어서 한다.
- **멈춤 표시(`RUN_DIR/PAUSED`)**: 코드를 바꾼 뒤 사용자 답을 기다리며 턴을 끝내야 할 때(열린 질문, 15단계 실패 보고)만 사유 1줄을 적어 만든다 — 이게 있으면 종료 시 품질 게이트가 막지 않고 알리기만 한다. **오류를 고치기 싫어서 만드는 것은 금지**이고, 만들 때는 `state.md` 에 멈춘 단계·이유를 함께 적는다. 게이트는 사유 없는 PAUSED 를 인정하지 않고, 같은 변경으로는 PAUSED 종료를 1회만 허용한다 — 답을 받았으면 반드시 지우고 검사를 통과시킨다.
- 새 작업이면 짧은 kebab-case 슬러그로 `RUN_DIR=.harness/runs/{slug}/`를 만들고 `task.md`에 요청 원문을 적는다.
- **기존 개발 기록 확인**: `spec/README.md`(spec 색인)가 있으면 읽고, 이번 요청과 관련된 기능의 spec(`spec/backend/`·`spec/frontend/` 의 md)을 찾아 읽는다. 기존 기능을 고치는 요청이면 그때 정한 요구사항·결정을 이어받고, 1단계 질문도 그 기록으로 답이 되는 건 묻지 않는다.
- **이번 요청의 spec 번호를 정한다** (`COMMON.md` §4 — 두 폴더를 합친 최대 번호 + 1). 이 번호와 기능명(kebab-case)을 backend·frontend spec-create 양쪽에 똑같이 넘긴다 — 한 요청 = 한 번호.
- **작업 브랜치 만들기 + 개발 방식 결정** (`COMMON.md` §3-B 1번):
  - `git switch dev` → 커밋 안 된 이전 변경이 있으면 사용자에게 "함께 / 따로 보관"을 묻는다 → `git switch -c feature/{NNN}-{slug}` (사용자가 "급하다·긴급"이라고 한 수정은 `hotfix/{NNN}-{slug}`). 이번 요청의 모든 커밋(spec·도우미 Task·merge·검증 반영)은 이 브랜치에 쌓이고, 14단계에서 전부 통과해야 dev 에 merge 된다 — 검증 안 된 코드는 dev 에 들어가지 않는다. 브랜치명을 `state.md` 에 적고, 재개할 때는 그 브랜치로 `git switch` 한 뒤 이어서 한다.
  - 그 다음 `git status --porcelain -- backend frontend` 가 비어 있으면 **워크트리 방식**(6단계를 서브에이전트들이 별도 작업 폴더에서 병렬 수행). 이전 변경을 "함께" 가져와 커밋 안 된 코드가 있으면 워크트리가 그 변경을 볼 수 없으므로 **직접 방식**(6단계를 메인이 이 폴더에서 묶음 순서대로 수행)으로 진행하고, 사용자에게 "저장되지 않은 이전 작업을 포함해서 이번엔 한 폴더에서 진행합니다"라고 한 줄 알린다. 방식은 `RUN_DIR/state.md` 에 적는다.
  - **판정은 이 시점에 1회만** 한다. 이후 spec·합치기·검증으로 생긴 변경은 이번 작업의 산출물이므로 다시 판정하지 않는다. (화면 도우미는 서버를 실행하지 않고 msw 로 계약을 흉내 내므로 서버 묶음과 동시에 돌아도 문제없다.)
  - 재개할 때는 `state.md` 의 배치표(5단계)를 읽고 `완료` 가 아닌 묶음부터 이어서 띄운다. `진행` 인데 도우미가 없으면 그 워크트리의 커밋을 확인해 남은 Task 만 맡긴다.

## 1. 요구사항 확정 (사용자와 대화)
코드를 쓰기 전에 아래를 **쉬운 말로** 최대 3~4개 질문해 확정한다. 이미 분명한 것은 묻지 않는다.
- 어떤 화면에서 무엇을 보고/입력하나? (목록, 상세, 작성 폼 등)
- 어떤 정보를 저장하나? (예: 제목, 내용, 작성자, 날짜)
- 정보끼리 **몇 개씩** 연결되나? (예: "게시글 하나에 사진 여러 장?", "한 사람이 여러 번 예약?", "태그 하나를 여러 글에?") — DB 설계의 근거가 되므로 저장이 필요한 요청이면 꼭 확인한다. 테이블·관계 같은 용어는 쓰지 않는다.
- 누가 쓸 수 있나? (모두 / 로그인한 사람 / 관리자)
- 기존 기능(예: 공지사항)과 비슷하게 하면 되나?

확정한 내용을 3~5줄 요약으로 보여주고 "이대로 만들까요?"라고 확인받는다. 이후로는 끝날 때까지 묻지 않고 진행한다(막힌 경우 제외).

## 2. 범위 판단
- **모든 개발 요청은 spec 문서를 남긴다** — 문구·색 하나 바꾸기, 버그 수정도 예외 없이 spec-create 를 거친다 (작은 요청은 Task 1개짜리 짧은 spec). 기록이 쌓여야 나중에 같은 기능을 고칠 때 읽을 수 있다.
- 데이터 저장·조회가 필요하면 → 서버 + 화면 (3~15 전부)
- 화면 모양·문구만 바꾸면 → 화면만 (3·8·9·11 생략, 계약은 기존 `swagger/docs.md`)
- 서버 동작만 바꾸면 → 서버만 (4·9·12 생략, 13은 정적 검증 + 기존 e2e)

## 3. 서버 spec
`backend/spec-create` 를 따른다 (vibe-build 모드) — 입력: 1단계 요구사항 + spec 번호·기능명 + 관련 기존 spec. 열린 질문이 생기면 비개발자 언어로 바꿔 사용자에게 묻는다.
- 저장할 정보가 새로 생기거나 바뀌면 **데이터 모델 설계**(`backend/db-design` 절차 + `db-design-reviewer` 에이전트 PASS)를 건너뛰지 않는다.
- **"API 설계" 섹션이 화면 개발의 계약이다** — 화면은 서버 완성을 기다리지 않고 이 섹션대로 만든다. 필드·타입·nullable·status·에러 메시지까지 빠짐없이 적혔는지 확인한다 (`backend/api-spec` 체크리스트).

## 4. 화면 spec
`frontend/spec-create` 를 따른다 (vibe-build 모드) — 입력: 화면 요구사항 + **짝 서버 spec 경로(API 설계 섹션이 계약)** + spec 번호·기능명(서버 spec 과 같은 번호) + 관련 기존 spec. 서버 개발을 기다리지 않고 3단계 직후 바로 쓴다.
> 서버 변경이 없는 요청(화면만)이면 기존처럼 `frontend/swagger/docs.md` 가 계약이다.

## 5. spec 검증 → 배치표 — 누가 무엇을 어느 순서로
**먼저 spec 검증**: Agent 도구로 **`spec-reviewer`** 를 호출한다 — 입력: 서버·화면 spec 절대경로, 1단계 요구사항 요약. `FAIL` 이면 지적대로 spec 을 고치고 다시 호출 (**최대 3회**), `QUESTIONS` 는 사용자에게 쉬운 말로 묻는다. 3회 안에 `PASS` 가 안 나오면 남은 지적을 사용자에게 알리고 멈춘다. 병렬 도우미들은 spec 을 그대로 믿고 동시에 만들므로, spec 결함은 도우미 수만큼 복제된다 — 계약 빈칸·Task 경계(커밋마다 green)·이름 규칙·동시 요청 순서 경쟁·기존 e2e 선택자 겹침을 여기서 잡는다. 결과를 `RUN_DIR/log.md` 에 적는다.
**PASS 후 spec 커밋** (워크트리 방식): spec 2개 + `spec/README.md` 를 명시적 경로로 add → `docs: spec {NNN} {기능명} 작성` (`COMMON.md` §3). 도우미 워크트리는 작업 브랜치의 HEAD 에서 갈라지므로 이 커밋이 있어야 워크트리 안에도 spec 이 들어간다. (이후 spec 의 체크박스·진행 로그·상태 갱신은 14단계 검증 반영 커밋에 포함.)

두 spec 의 Task 마다 적힌 **`묶음`** 으로 개발 도우미를 나눈다 (묶음 규칙의 단일 출처: **`COMMON.md` §5**). `RUN_DIR/state.md` 에 아래 표를 적는다 — 6·7단계와 재개(0단계)가 이 표를 기준으로 한다.

```markdown
| 묶음 | 도우미 | 기반 묶음 | Task | 상태 | 브랜치 | 워크트리 |
|---|---|---|---|---|---|---|
| 서버-기반 | backend-dev | — | 1 | 대기 | | |
| 서버-comment | backend-dev | 서버-기반 | 2~4 | 대기 | | |
| 서버-tag | backend-dev | 서버-기반 | 5~7 | 대기 | | |
| 화면-comment-데이터 | frontend-dev | — | 1~4 | 대기 | | |
| 화면-comment-목록 | frontend-dev | 화면-comment-데이터 | 5 | 대기 | | |
```
- 상태: `대기` → `진행` → `기반 준비`(마지막 Task 커밋 완료, 도우미는 마무리 검사 중) → `완료` | `실패` → `합침`. 기반 묶음이 `기반 준비` 이상이면 그 위 묶음을 시작할 수 있다 (6단계).
- **동시에 도는 도우미는 최대 4개.** 서버 묶음과 화면 묶음은 서로 기다리지 않는다 (화면은 계약으로 만들고 API 는 msw 로 흉내 낸다).
- 묶음이 1개뿐인 영역은 나누지 않고 도우미 1개가 전부 한다.

## 6. 병렬 개발 — 서브에이전트 + 워크트리
**시작할 수 있는 묶음(기반이 없거나 기반이 `기반 준비` 이상)을 빈 자리(최대 4) 만큼 한 메시지에서 동시에** Agent 도구로 호출한다 — 서버 묶음은 **`backend-dev`**, 화면 묶음은 **`frontend-dev`**, 모두 **`isolation: "worktree"`**. 도우미 하나가 끝나 알림이 오면 표를 갱신하고, 그 묶음을 기반으로 하는 묶음과 남은 묶음을 빈 자리만큼 다시 띄운다. 모든 묶음이 `완료` 가 될 때까지 반복한다.
- **기반 묶음은 마지막 Task 커밋이 보이는 즉시 위 묶음을 띄운다** — 도우미의 완료 보고(마무리 검사 몇 분)를 기다리지 않는다. Monitor 에서 기반 브랜치에 그 묶음의 마지막 Task 커밋(커밋 메시지의 `Task {k}`)이 나타나면 표를 `기반 준비` 로 바꾸고, 그 **커밋 해시**를 기반으로 위 묶음을 호출한다. `fix:` 커밋도 `(spec {NNN})` 접미사로 같은 브랜치에 오므로 함께 알린다. 기반 도우미가 마무리 검사에서 `fix:` 커밋을 더 만들면, 그 기반 위에서 돌고 있는 도우미들에게 SendMessage 로 "`git merge {기반 브랜치}` 로 받아라" 를 알린다. 기반 도우미가 실패로 끝나면 위 묶음들을 멈추게(SendMessage) 하고 실패 처리로 간다.
- 빈 자리는 기반 묶음(화면 묶음들을 막고 있는 것)에 먼저 준다.
- **끝난 묶음은 바로 작업 브랜치에 merge 한다** (7단계 절차, 기반 순서는 지킴) — 특히 **마이그레이션을 담은 묶음은 끝나는 즉시** 합친다: 그 도우미가 공유 DB 를 이미 새 리비전으로 올려서, merge 전까지 메인 폴더 코드가 DB 보다 뒤처져 메인의 종료 검사(`alembic check`)가 깨진다. 다른 묶음의 기반으로 쓰이는 브랜치는 위 묶음이 모두 merge 될 때까지 지우지 않는다.

프롬프트에 넣을 것 (공통):
- 메인 폴더 절대경로, spec 절대경로(`{메인}/spec/{backend|frontend}/{NNN}-*.md`) — 5단계 커밋으로 워크트리에도 있지만, 이후 메인이 고칠 수 있으므로 **최신본은 메인 경로에서 읽기만** 하게 한다.
- **담당 묶음 이름과 Task 번호** — 이 Task 만 구현한다.
- **기반**(기반 묶음이 있을 때) — 기반 브랜치 이름 + 시작 커밋 해시(`기반 준비` 시점의 마지막 Task 커밋). 시작할 때 그 커밋을 fast-forward 로 가져와서 그 위에서 작업한다.
- 화면 묶음: 계약 = 짝 서버 spec 의 "API 설계" 섹션 절대경로 (서버 변경 없는 요청이면 `{메인}/frontend/swagger/docs.md`).
- 화면 새 페이지 규칙: 화면은 `frontend/src/features/{도메인}/pages/{X}Page.tsx`, `frontend/src/app/{경로}/page.tsx` 는 import 후 `export default` 만(+ `metadata`). 메뉴(`AppShell.tsx` 의 `NAV_ITEMS`)는 기반 묶음 몫이다 (`COMMON.md` §5).

**기다리는 동안 사용자에게 진행 상황을 알린다** (도우미는 수 분~수십 분 걸리고 그동안 아무 말이 없으면 비개발자는 멈춘 줄 안다):
- 도우미를 띄운 직후 한 줄: "서버·화면을 나눠서 동시에 만드는 중입니다 — 작업 {M}개를 도우미 {K}명이 맡았고, 끝나면 자동으로 이어갑니다. 다시 말씀하지 않으셔도 됩니다."
- Monitor 로 도우미 브랜치(`worktree-agent-*`)들의 커밋을 지켜본다 — 새 커밋 제목을 한 줄씩 내보내고, 표의 모든 묶음이 끝나거나 브랜치가 사라지면 끝나는 스크립트로. 커밋이 올 때마다 "{N}/{M} 완료 — {Task 제목을 화면·동작 말로}" 한 줄을 알린다.
- 사용자가 중간에 물으면 브랜치별 커밋 수와 워크트리 변경 파일(`git -C {워크트리} status --short`)로 지금 어느 Task 인지 답한다. "자동 알림을 기다린다"고만 답하지 않는다.

도우미는 Task 마다 레이어 rules·기술 스킬을 메인 경로에서 읽고 구현·테스트한 뒤, 커밋 규칙을 확인해 **Task별로 커밋**한다. 결과로 **브랜치명·워크트리 경로·Task별 통과 여부·테스트 수·커밋 해시와 메시지·공유 파일 요청·막힌 점**을 받아 표에 적는다. 보고의 커밋 메시지가 규칙에 어긋나 보이면 원인을 확인한다. 막힌 점(열린 질문)이 있으면 사용자에게 쉬운 말로 묻고, 답을 넣어 같은 서브에이전트를 이어서 실행(SendMessage)한다.

**도우미가 "같은 에러 3회 연속 실패로 중단"을 보고하면:**
1. 보고의 실패 요약으로 `docs/TROUBLESHOOTING.md` 와 영역 문서(`docs/{backend,frontend}/TROUBLESHOOTING.md`)에서 같은 증상을 찾는다. 해결법이 있으면 그 내용을 넣어 같은 서브에이전트를 SendMessage 로 이어서 실행한다.
2. 원인이 spec 쪽(요구사항 모순·누락, 계약 오류)이면 spec 을 고치고(필요하면 사용자에게 쉬운 말로 확인) 같은 서브에이전트를 이어서 실행한다. 계약(API 설계)을 고쳤으면 이미 그 계약으로 만든 묶음에도 바뀐 점을 SendMessage 로 알린다.
3. 1·2 를 합쳐 **묶음마다 재개는 1회만.** 그래도 실패하거나 원인이 환경(DB·Docker·포트·설치)이면 그 묶음을 `실패` 로 적고, 그 묶음을 기반으로 하는 묶음은 띄우지 않는다. **이미 돌고 있는 다른 도우미는 끝까지 받은 뒤 멈춘다** — 워크트리는 지우지 않고 표·실패 요약을 `RUN_DIR/state.md` 에 남긴 뒤 15단계 실패 보고로 간다 (합치기·이후 단계·커밋 진행 금지).

> **직접 방식이면**: 메인이 표의 순서대로(기반 먼저) 묶음마다 `backend/spec-run`·`frontend/spec-run`(vibe-build 모드)을 이 폴더에서 따른다 (Task 커밋 없이). 7단계는 건너뛴다.

## 7. 합치기 — 도우미 브랜치를 작업 브랜치에 merge
표의 **기반 묶음부터** 순서대로, 묶음마다 도우미 브랜치를 작업 브랜치에 merge 한다 — 도우미의 Task별 커밋이 기록에 그대로 남는다. 메시지는 `COMMON.md` §3 규칙(커밋 직전 훅이 merge 메시지도 검사):
```bash
git merge --no-ff {도우미 브랜치} -m "chore: {묶음} 묶음 합치기 (spec {NNN})"
git worktree remove --force {워크트리 경로} && git branch -d {도우미 브랜치}   # 그 브랜치를 기반으로 쓰는 묶음이 모두 merge 된 뒤
cd backend && .venv/bin/alembic upgrade head                                     # 마이그레이션 묶음을 merge 했으면 (이미 적용됐으면 변화 없음)
```
- 기반 위 묶음은 기반 커밋을 이미 품고 있으므로 git 이 중복 없이 합친다. 메인 폴더에 미커밋 변경(진행 중 수정)이 있어도 merge 가 같은 파일을 건드리지 않으면 진행된다.
- merge 가 **충돌**하면 `git merge --abort` 로 되돌리고 멈춰 원인(두 묶음이 같은 파일을 고침 = 묶음 규칙 위반, 또는 메인 폴더에 같은 파일의 미커밋 변경)을 보고한다. 충돌을 한쪽으로 덮어써서 해결하지 않는다.
- 도우미 보고의 **공유 파일 요청**(묶음 규칙상 직접 못 고친 것)이 있으면 여기서 메인이 반영하고 해당 영역 테스트를 다시 돌린다 (미커밋 — 14단계 검증 반영 커밋에 포함).
- 전부 합친 뒤 `make check` 를 1회 돌려 묶음끼리 어긋난 곳(import·타입)과 **화면 빌드**를 확인하고, 실패하면 메인이 고친다. (화면 도우미는 빌드를 하지 않는다 — 도우미 4명이 동시에 빌드하면 기계가 몰려 느려지고 테스트가 시간 초과로 흔들린다. 전체 빌드는 여기서 메인이 1회.)
- 도우미 보고의 **기존 e2e 겹침**(바꾼 문구와 부분 일치하는 기존 e2e 선택자)이 있으면 12단계에서 그 e2e 를 먼저 고친다.
- spec 문서의 Task 체크박스·진행 로그·상태는 서브에이전트 보고를 근거로 **메인이** 갱신한다.

## 8. API 문서 동기화
`backend/sync-api-docs` 를 따른다 (vibe-build 모드) — 입력: 대상 도메인. 서버 변경이 없는 요청이면 건너뛴다.

## 9. 계약 대조 — 실제 서버 ↔ 화면이 믿은 계약
**기계 대조** (눈으로 하지 않는다) — 레포 루트에서:
```bash
backend/.venv/bin/python backend/scripts/check_contract.py spec/backend/{NNN}-*.md
```
서버 spec 「API 설계」의 엔드포인트마다 실제 앱(`app.openapi()`·스키마 클래스·코드)과 비교한다 — 엔드포인트 존재, query·path 파라미터 이름, status, Response 필드 이름, 에러 message 글자. 필드 **타입·nullable** 은 스크립트가 보지 않으므로 8단계 docs.md 와 spec 표를 메인이 함께 확인한다.
- exit 0 이면 통과. `RUN_DIR/state.md` 에 "계약 대조 통과" 를 적는다.
- 다르면 **spec(계약)이 기준**이다 — 서버 코드를 spec 대로 고친다. spec 대로가 불가능한 이유가 있으면 spec 의 API 설계를 고치고, 그 계약으로 만든 화면 코드(models 스키마·Mapper·msw 테스트 데이터)도 같이 고친다. 고친 뒤 8단계를 다시 하고 양쪽 테스트(`pytest`·`pnpm test`)를 돌린다.

## 10. 리팩토링
`backend/refactor` → `frontend/refactor` 를 적용 모드로 따른다 (vibe-build 모드) — 대상: 워크트리 방식은 **`--spec {NNN} --apply`**(도우미 Task 커밋이 작업 브랜치에 남아 있으므로 `(spec {NNN}` 커밋들이 바꾼 파일) + 워킹트리 미커밋 변경, 직접 방식은 `--apply`(워킹트리 변경 파일). 수정이 있으면 해당 영역 테스트(`pytest` / `pnpm test`)를 다시 돌려 회귀 없음을 확인한다. "사용자 확인 필요" 항목은 적용하지 않고 15단계 보고에 넣는다.

## 11. 서버 검증
`backend/verify` 를 따른다 (vibe-build 모드) — 이번 spec 의 엔드포인트 전부를 서버를 켜서 실제로 요청해 status code·응답 형식(envelope)을 확인한다. 고칠 게 생기면 메인이 직접 고치고 테스트를 다시 돌린다.

## 12. 화면 검증 — MCP 실검증 → e2e 고정
화면 spec 의 UI Task(페이지·컴포넌트)마다 `frontend/browser-check` 를 따른다 — Playwright MCP 로 실제 브라우저에서 눌러보며 콘솔·API 에러 0 확인(`RUN_DIR/mcp-check.md`) → 그 흐름을 `frontend/e2e/{기능}.spec.ts` 로 고정해 통과(`e2e/fixtures.ts`의 `test` import).
- 7단계에서 모은 **기존 e2e 겹침**을 먼저 고친다 (선택자를 `exact: true` 등으로 정확히 — 테스트 약화가 아니라 새 문구와 구분하는 것).
- MCP 브라우저가 열리지 않으면(`Browser is already in use` — 다른 Claude 창이 점유) 기다리거나 우회하지 말고, 같은 흐름을 e2e 로 먼저 작성·실행해 판정하고 `mcp-check.md` 에 "MCP 불가 → e2e 판정" 과 사유를 적는다 (`frontend/browser-check` 「vibe-build 모드」). (`.mcp.json` 의 `--isolated` 로 창마다 따로 띄우게 되어 있으므로, 이 메시지가 나오면 설정이 적용되기 전 세션이다.)

## 13. 최종 검증 루프 (하네스)
이 폴더의 `harness.md`(`.claude/skills/vibe-build/harness.md`)를 읽고 따른다 — 입력: "{slug} 최종 검증". 루프 규칙(최대 6회, 2바퀴 연속 개선 없으면 중단, 명령 결과·로그로만 판정)은 그 파일이 정한다. 루프 상태는 `RUN_DIR/loop.md` 에 쓰고, `state.md`(배치표·브랜치·방식)는 건드리지 않는다.
- 정적: `make check`
- 동적: 바퀴마다 `RUN_DIR/console-errors.log` 를 비우고 `make e2e HARNESS_RUN_DIR=<RUN_DIR>` → 그 로그로 판정 (세는 법은 `harness.md`)
- 통과하면 `RUN_DIR/DONE` 파일을 만든다. **통과하지 못하면 14단계(커밋)로 가지 않는다.**

## 14. 커밋 → dev merge — 규칙 문서를 읽고
절차는 **`COMMON.md` §3** (규칙 문서 Read → 메시지 확인 → 명시적 경로 add → 커밋, push 금지). 이 단계에서 정할 것만:
1. spec 상태를 `✅ 완료`로 갱신 (spec 문서 2개 + `spec/README.md` 색인 줄) — Task 체크박스·진행 로그(도우미 커밋 해시)도.
2. **해결한 오류 기록**: 이번 작업 중 고치는 데 2번 이상 걸린 오류(`RUN_DIR/log.md`, 도우미 보고, Stop 훅 차단)가 있고 TROUBLESHOOTING 에 아직 없으면, 알맞은 문서(`docs/TROUBLESHOOTING.md` 공통 / `docs/{backend,frontend}/TROUBLESHOOTING.md`)에 기존 형식(`## 제목` + 증상·원인·해결)으로 1항목씩 추가하고 add 대상에 넣는다.
3. **검증 반영 커밋** (작업 브랜치) — add 대상 = 7~13단계에서 메인이 바꾼 파일만: 공유 파일 요청 반영, 리팩토링, `frontend/swagger/docs.md`, 계약 대조 수정, `frontend/e2e/*.spec.ts`, spec 문서·색인, 2번 TROUBLESHOOTING. 메시지 `{type}: {요약} 검증 반영 (spec {NNN})` (바뀐 게 spec·문서뿐이면 `docs:`). 이번 요청과 무관한 미커밋 변경은 넣지 않는다.
4. **dev 에 merge** (`COMMON.md` §3-B 3번) — `git switch dev` 와 merge 는 각각 별도 Bash 호출: `git merge --no-ff feature/{NNN}-{slug} -m "{type}({도메인}): {기능 요약} (spec {NNN})"` → `git branch -d feature/{NNN}-{slug}`. merge 메시지 첫 줄 끝에 **`(spec {NNN})`**, 본문에 사용자 관점 변경 요약. dev 에는 이 merge 커밋 1개가 기능 단위로 보이고, 그 아래에 spec·Task·묶음 합치기·검증 반영 커밋이 남는다 (refactor 스킬 `--spec`·vibe-refactor 가 `git log --grep="(spec {NNN}"` 로 이 커밋들을 찾는다). 충돌하면 `git merge --abort` → 작업 브랜치로 돌아가 15단계 실패 보고. main 에는 merge 하지 않는다 (사람이 직접).
> 직접 방식이면 3번 커밋의 add 대상이 이번 요청 전체다 — 코드·테스트·마이그레이션·`data-model.yaml`·spec 문서·색인·docs.md·e2e·TROUBLESHOOTING (메시지 첫 줄 끝에 `(spec {NNN})`). 이전 변경을 "함께" 가져왔으면 그 파일도 포함한다. 4번은 같다.

> 참고: 작업을 끝내려 할 때 Stop 훅(품질 게이트)이 lint·타입·테스트·테스트 누락·e2e 를 다시 돌린다. 실패하면 종료가 막히고 에러가 돌아오니, 그 에러를 고친다. 테스트를 지우거나 skip해서 통과시키는 것은 금지.
> 이 훅은 **턴이 끝날 때마다** 돈다. 진행 중 run(`RUN_DIR` 에 `DONE` 없음)이 있는 동안에는 오래 걸리는 e2e 를 미루고 lint·타입·테스트·테스트 누락만 검사하므로, 중간 질문 턴은 그 정적 검사만 통과하면 된다. e2e 는 13단계(harness)가 통과시켜 `DONE` 을 만든 뒤 마지막 종료에서 다시 돈다 — 그래서 13단계 통과 없이 `DONE` 을 만들면 안 된다.

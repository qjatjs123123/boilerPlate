# schema-cleanup — 쌓인 DB 구조를 정리한다 (사용자 확인 필수)

요청마다 설계하다 보면 예방 장치(`db-design` 0단계·reviewer·스키마 검사)를 거쳐도 구조 부채가 남는다. 이 절차가 **치우는 길**이다.
정리는 기존 데이터를 옮기는 일이라 CLAUDE.md 의 "구조 대규모 변경·데이터 삭제는 확인" 규칙에 해당한다 — **정리안을 보여주고 확인받기 전엔 아무것도 바꾸지 않는다.**

## 1. 부채 수집 (읽기만)

1. `backend/data-model.yaml` 전체, `docs/backend/DOMAIN-MAP.md`, `docs/backend/ERD.md`
2. `spec/backend/*.md` 의 「구조 부채」 메모 — 아직 처리 안 된 것
3. `make gc` 「데이터 구조」 결과(미사용 테이블·개념 지도에 없는 테이블), `cd backend && .venv/bin/pytest -q tests/architecture` 결과, `known-violations.json` 의 `schema-*` 항목
4. `db-design` 0단계를 **현재 모든 FR** 대상으로 다시 수행 — "처음부터 다시 설계한다면" 의 전체 구조와 지금 구조의 차이

찾을 것:

| 부채 | 예 | 정리 방향 |
|---|---|---|
| 의미가 같은 테이블 두 개 | `notices` + `posts` | 하나로 합치고 종류 enum |
| 규칙이 같은 행동 테이블 | `post_likes` + `post_bookmarks` (규칙 차이 없음) | `post_reactions` + `reaction_type` |
| 1:1 로 쪼개진 부가 정보 | `post_settings` (글마다 1행) | 원래 테이블 컬럼으로 |
| 안 쓰는 테이블·컬럼 | gc 미사용 테이블 보고, 어떤 FR 에도 대응 안 되는 컬럼 | 제거 (데이터 보관 여부 확인) |
| 개념 지도에 없는 테이블 | gc 「데이터 구조」 경고 | 개념 행 추가 또는 제거 |

부채가 없으면 "정리할 구조가 없어요" 라고 알리고 끝낸다.

## 2. 정리안 + 데이터 영향표

부채마다 아래를 만든다 (내부용 — 사용자에겐 3단계의 쉬운 말로):
- 바뀌는 테이블·컬럼 (전 → 후 yaml)
- **데이터 영향표**: 어떤 데이터가 어디로 옮겨지는지, 지워지는 데이터가 있는지, 옮길 때 값이 바뀌는지(예: 북마크 → `reaction_type='bookmark'`)
- 영향받는 API·화면 — 응답 모양이 바뀌면 그 화면도 고쳐야 한다 (`spec/README.md` 로 관련 spec 찾기)
- 되돌리기 가능 여부 (downgrade 로 원래대로 나눌 수 있나)

## 3. 사용자 확인 (화면·생활 언어, 하나씩)

```
저장 구조를 살펴보니 정리하면 좋을 곳이 {n}군데 있어요. 화면과 기능은 그대로 둡니다.
 1. '좋아요'와 '북마크'가 같은 모양으로 따로 저장되고 있어요 → 한 곳에 모으고 종류로 구분할까요?
    - 기존 좋아요 {a}건·북마크 {b}건은 그대로 옮겨져요. 지워지는 건 없어요.
 2. 아무 화면에서도 쓰지 않는 '임시 신고' 저장 공간이 있어요 → 지울까요? (안에 든 {c}건도 같이 지워져요)
어떤 번호를 진행할까요? (원하지 않으면 그대로 둡니다)
```
- 지워지는 데이터가 있으면 **건수와 함께** 따로 확인받는다. 답이 애매하면 진행하지 않는다.
- 고르지 않은 항목은 바꾸지 않고, 해당 spec 「구조 부채」 메모에 "보류 (YYYY-MM-DD 사용자 결정)" 로 남긴다.

## 4. 실행 — vibe-build 흐름 그대로

사용자가 고른 항목을 **요구사항으로 확정된 요청**으로 보고 `.claude/skills/vibe-build/SKILL.md` 를 **0단계부터** 따른다 — 0단계(RUN_DIR·spec 번호·`dev` 에서 작업 브랜치 `feature/{NNN}-schema-cleanup-{요약}` 생성)는 그대로 하고, **1단계(요구사항 확인)만 건너뛴다** (이 절차의 3단계로 끝났다). spec 기능명은 `schema-cleanup-{요약}`. 추가 규칙:

- **서버 spec**: 「데이터 모델」에 결정 기록 = "정리 — {부채} (사용자 확인 YYYY-MM-DD)", 전·후 yaml, 데이터 영향표. db-design-reviewer PASS 필수.
- **models Task 의 마이그레이션은 데이터 이동을 직접 작성**한다 — autogenerate 만으로는 데이터가 사라진다. 순서: 새 구조 생성 → `INSERT … SELECT` 로 옮기기 → 옛 구조 제거. `downgrade` 도 반대로 작성.
- **데이터 이동 테스트** (models Task 테스트에 포함): 옛 구조에 샘플 행을 넣고 → `upgrade` → 새 구조의 건수·값이 같은지 → `downgrade` → 원래대로인지.
- **동작 유지**: 기존 API 응답 모양·화면 동작은 그대로가 원칙. 기존 테스트·e2e 는 고치지 않고 그대로 통과해야 한다 (응답 모양이 꼭 바뀌어야 하면 3단계에서 화면 영향까지 확인받은 경우만, 그 화면 spec 도 함께).
- 끝나면 `DOMAIN-MAP.md`·`ERD.md` 갱신, 처리한 「구조 부채」 메모에 "해결 — spec {NNN}" 표시.

## 5. 사용자 보고

```
✅ 저장 구조를 정리했습니다. 화면과 기능은 그대로예요.
- 정리한 것: {사용자 관점 — 예: "좋아요·북마크를 한 곳에 모았어요 (옮긴 데이터 {a+b}건, 빠진 것 없음)"}
- 그대로 둔 것: {고르지 않은 항목}
```

## 금지
- 3단계 확인 없이 구조 변경·데이터 이동·삭제
- 데이터 이동 없이 autogenerate 마이그레이션만으로 테이블 합치기/나누기
- 기능 요청(vibe-build) 도중에 정리를 끼워 넣기 — 그때는 「구조 부채」 메모만 남긴다
- 테스트 약화, `known-violations.json` 에 항목 추가, `git push`

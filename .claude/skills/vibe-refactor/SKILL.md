# vibe-refactor — 동작은 그대로, 코드만 정리

사용자는 비개발자다. 코드를 보여주지 말고 **화면·동작 기준**으로 소통한다.
**동작이 바뀌면 리팩토링이 아니다** — 화면에 보이는 것·버튼 동작이 달라지는 변경은 하지 않는다 (그건 vibe-build).

아래 `frontend/refactor`·`backend/refactor` 표기는 **`.claude/skills/{영역}/refactor/SKILL.md` 파일을 Read 로 읽고 따른다**는 뜻이다. 슬래시 커맨드가 아니며, 같은 이름의 전역 커맨드가 목록에 보여도 쓰지 않는다.

## 0. 준비
- 개발 환경이 준비 안 됐으면 vibe-setup 스킬을 먼저 따른다.
- 진행 중인 작업(`.harness/runs/` 에 `DONE` 없는 run)이 있으면, 그 작업을 먼저 끝낼지 사용자에게 묻는다 — 만들다 만 코드를 정리하면 꼬인다.
- **작업 브랜치**: 1단계에서 대상이 정해지면 `COMMON.md` §3-B 1번대로 `dev` 에서 `feature/refactor-{slug}` 를 만든다 (커밋 안 된 이전 변경은 "함께 / 따로 보관"을 묻는다 — "방금 만든 거 정리해줘"처럼 그 변경이 정리 대상이면 묻지 않고 함께 가져간다). DB 구조 정리는 vibe-build 흐름이 브랜치를 만든다.

## 1. 대상 정하기
사용자 말에서 범위를 고른다. 분명하지 않을 때만 쉬운 말로 1번 묻는다.

| 사용자 말 | 대상 |
|---|---|
| "방금 만든 거 정리해줘" / 범위 언급 없음 | 아직 커밋 안 된 변경 파일 (없으면 `git log --grep="(spec " -1` 로 찾은 최근 vibe-build 커밋의 spec 번호 → refactor 스킬 `--spec {NNN}`) |
| "공지사항 화면 정리해줘" | 그 기능 폴더 — `frontend/src/features/{도메인}/` (+ 서버 쪽도 원하면 `backend/app/domains/{도메인}/`) |
| "DB 정리해줘" / "저장 구조 정리해줘" / 주간 점검이 구조 정리를 제안 | **데이터 구조 정리** — 이 스킬의 2~5단계 대신 `backend/schema-cleanup`(`.claude/skills/backend/schema-cleanup/SKILL.md`)을 읽고 따른다. 데이터를 옮기는 일이라 그 절차의 사용자 확인을 반드시 거친다 |
| "전체 다 정리해줘" | `frontend/src/` 와 `backend/app/` 전체 — 파일이 50개 넘으면 기능 단위로 나눠 순서대로 진행한다고 알린다 |

정리 전에 `spec/README.md` 색인에서 대상 기능의 spec(`spec/{backend,frontend}/*.md`)을 찾아 읽고, 그 기능이 **원래 어떻게 동작해야 하는지**를 확인한다 — 정리 후에도 그 동작이 그대로여야 한다.

화면 쪽(`frontend/`)이 있으면 `frontend/refactor`, 서버 쪽(`backend/`)이 있으면 `backend/refactor` 를 각각 **vibe-refactor 모드**(`COMMON.md` §2-B)로 따른다 — 하위 refactor 스킬은 커밋하지 않고, 커밋은 4단계에서 이 스킬이 1회 한다.

## 2. 검토 → 사용자에게 쉬운 말로 요약
각 refactor 스킬의 검토 단계(보고서)까지 먼저 수행한다. 보고서 원문은 보여주지 않고 이렇게 바꿔 말한다:

```
정리할 거리를 찾았어요.
바로 고칠 수 있는 것 (동작 변화 없음): {n}건
 - 예: 같은 숫자가 여러 군데 흩어져 있던 것 한 곳으로 모으기
확인이 필요한 것 (구조가 바뀜): {m}건
 1. 공지사항·FAQ 목록에 똑같은 표 모양이 두 벌 있어요 → 하나의 공통 표로 합칠까요?
 2. ...
```

- "바로 고칠 수 있는 것"은 각 refactor 스킬의 **자동 수정 OK** 목록에 해당하는 것만.
- "확인이 필요한 것"(공통 컴포넌트로 빼기, 훅 분리, 파일 이동, 이미지 부품 교체 등)은 **하나씩 화면 기준 설명**을 붙이고 번호로 고르게 한다. 중복 통합 제안에는 "앞으로 두 화면이 서로 다르게 바뀔 수 있으면 합치지 않는 게 낫다"는 판단을 한 줄 덧붙인다.

## 3. 적용
1. 자동 수정 항목 → 각 refactor 스킬의 적용(`--apply`) 절차대로 수정.
2. 사용자가 고른 구조 변경 → 해당 rules(`.claude/rules/{frontend,backend}/*.md`)의 위치·폴더 규칙대로 수정. 공통 컴포넌트는 `frontend/refactor` 의 「공통 컴포넌트로 뺄 수 있는가」 표 기준.
3. 기존 테스트는 고치지 않는다 — 리팩토링 후에도 **그대로 통과해야** 한다. 옮긴 파일의 테스트 import 경로 수정만 허용. 새로 뺀 공통 컴포넌트·함수에는 테스트를 추가한다.

## 4. 검증
- `make check` (lint·타입·테스트) 통과 필수. 실패하면 고쳐서 다시 — 테스트 약화(skip·삭제·기대값 조작) 금지.
- 화면 구조를 바꿨으면(컴포넌트 추출·이동, `Image`/`Link` 교체 등) `.claude/skills/vibe-build/harness.md`(최종 검증 루프)를 읽고 따른다 — 입력: "{slug} 리팩토링 검증". 루프는 커밋하지 않으니 통과 후 아래 커밋은 이 스킬이 한다. 화면 흐름이 전과 같게 동작하는지 Playwright 로 확인.
- 통과하면 작업 브랜치에서 수정한 파일만 **명시적 경로로 `git add`** 후 `refactor: {대상 요약}` 으로 **1회** 커밋 (`COMMON.md` §3 — 규칙 문서 Read, `git add -A`·push 금지).
- 이어서 **dev 에 merge** (`COMMON.md` §3-B 3번 — 브랜치 전환과 merge 는 별도 Bash 호출): `git switch dev` → `git merge --no-ff feature/refactor-{slug} -m "refactor: {대상 요약}"` → `git branch -d feature/refactor-{slug}`. 검증을 통과하지 못하면 merge 하지 않는다.

## 5. 사용자 보고 (쉬운 말)
```
✅ {대상} 코드를 정리했습니다. 화면과 동작은 그대로예요.
- 정리한 것: {사용자 관점 2~4개 — 예: "공지·FAQ가 같은 표 부품을 쓰도록 합쳤어요"}
- 확인 방법: 평소처럼 {경로} 화면을 써 보시면 됩니다 (앱이 꺼져 있으면 "보여줘")
- 남겨 둔 것: {고르지 않은 제안이 있으면 한 줄씩}
- 개발용 버전(dev)에 반영했어요. 실제 배포용(main) 반영은 직접 해 주세요.
```

## 금지
- 화면 모양·문구·동작이 바뀌는 수정 (필요하면 vibe-build 로 넘긴다고 알린다)
- 사용자 확인 없이 컴포넌트 추출·파일 이동·공통 부품 통합
- 데이터 구조(DB·API 응답 모양) 변경 — DB 구조 정리는 위 「데이터 구조 정리」 행대로 `backend/schema-cleanup` 절차로만
- `main`·`dev` 에 직접 커밋, 검증 통과 전 dev 에 merge, main 에 merge
- 테스트 약화, `git push`
